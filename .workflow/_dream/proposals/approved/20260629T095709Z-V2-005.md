# Praetor Dream Playbook

Curated long-term engineering memory, consolidated out-of-band from completed
`.workflow/<slug>` tasks. This file is the **input store**: it is read-only to the
consolidation step and is only ever modified by `approve.py` promoting a reviewed
proposal. Every entry carries a machine-readable marker with stable ID + provenance;
see `.workflow/_dream/README.md`.

Do not hand-edit entry markers. Add or change entries through the dream loop so the
conservation invariant and ledger stay intact.

## General Rules

<!-- entry id=GR-0001 source=task-001 sha=38e3ca0 status=active -->
- **GR-0001** - The enforced Python minimum for this project is **3.11+** (human-approved, task-001 review). Do not introduce syntax, stdlib features, or third-party dependency constraints that require Python 3.12+ without re-confirming the floor with a human reviewer. _(task-001 @38e3ca0)_

<!-- entry id=GR-0002 source=task-002 sha=6fccc79 status=active -->
- **GR-0002** - When docs name a field but do not specify its nested structure, use the narrowest allowable opaque type (`dict[str, Any]` or `list[dict[str, Any]]`) and log the gap in `review.md` with the owning downstream task; do not invent sub-model fields to "complete" a shape, because invented structure drifts from the task that will own the real definition. _(task-002 @6fccc79)_

<!-- entry id=GR-0003 source=TASK-003 sha=3112332 status=active -->
- **GR-0003** - When implementing a hashing or serialization primitive reveals an underspecified contract in `docs/contracts.md` (missing field ordering, unspecified preimage, ambiguous input tuple, etc.), fix the doc first with explicit human approval before writing matching code. A code-only default that silently assumes the gap is a latent cross-site divergence hazard. _(TASK-003 @3112332)_

<!-- entry id=GR-0004 source=TASK-010 sha=198f6ff status=active -->
- **GR-0004** - When a hash or serialization formula is pinned in `docs/contracts.md`, add a companion test-vector test that asserts the exact output (e.g., a known SHA-256 hex digest) for a fixed known input. This guards against silent formula drift caused by changes to domain strings, delimiter ordering, or canonical serialization behavior across reimplementations. _(TASK-010 @198f6ff)_

<!-- entry id=GR-0005 source=TASK-018 sha=536aa57 status=active -->
- **GR-0005** - To deterministically test the race window between a pre-check and an in-transaction re-check (without real concurrency), add an underscore-prefixed keyword-only `None`-defaulting callable parameter (e.g., `_test_before_emit_transaction`) to the production function; the test injects a second real SQLite connection that commits in that window. This makes the in-tx re-check branch live under the suite and is more reliable than threading; the TASK-018 gatekeeper accepted this seam as pragmatic. _(TASK-018 @536aa57)_

<!-- entry id=GR-0006 source=TASK-020 sha=f15fc88 status=active -->
- **GR-0006** - Verification ledger counts (e.g., '15 passed') must be taken from running the listed command verbatim at write time — never projected or inferred from collect-only output; TASK-020 caught stale counts (17/25 vs actual 15/23) only via a post-hoc `pytest --collect-only` audit, after incorrect projected totals had already been written to the ledger. _(TASK-020 @f15fc88)_

<!-- entry id=GR-0007 source=TASK-027 sha=330da72 status=active -->
- **GR-0007** - Tests that invoke real external providers — requiring API keys or producing non-deterministic outputs — must carry a designated pytest marker (e.g., `integration` or `probabilistic`) so they are deselected from the default `pytest -q` gate; manual invocation instructions and required env-vars must be documented in a dedicated operator reference (e.g., `docs/eval_gates.md`), not only in source comments, so CI remains fully deterministic. _(TASK-027 @330da72)_

<!-- entry id=GR-0008 source=TASK-029 sha=c572cf3 status=active -->
- **GR-0008** - A pytest marker that deselects tests from the default CI gate (e.g., `@pytest.mark.integration`) must only be applied to tests that genuinely require external APIs, API keys, or non-deterministic network I/O; applying it to tests backed exclusively by local fixtures silently removes real behavioral coverage from the default `pytest -q` run, leaving production regressions undetected in CI. TASK-029 REVIEW-001 caught this as a blocker: all 12 compliance tests were excluded from CI despite having no external dependencies. _(TASK-029 @c572cf3)_

<!-- entry id=GR-0009 source=TASK-033 sha=9db3882 status=active -->
- **GR-0009** - Any tool that produces committed generated artifacts (e.g., compiled SPL files, exported JSON schemas) must expose a `--check` mode that exits non-zero when on-disk output differs from freshly generated output, alongside a `--write` mode that overwrites; CI gates run `--check` without side-effects while developers invoke `--write` to regenerate. Without `--check`, stale committed artifacts silently diverge from their generator with no automated signal. _(TASK-033 @9db3882)_

<!-- entry id=GR-0010 source=TASK-035 sha=1d08cfe status=active -->
- **GR-0010** - A performance benchmark is only trustworthy if it exercises the exact production code path; any dimension it does not actually measure separately (e.g. burst vs sustained rate) must be surfaced with an explicit flag such as `burst_separately_measured=False` rather than aliased to a measured value, and every reported result must carry its measurement context (hardware, uncontended vs contended) and never be cited as a production SLA. _(TASK-035 @1d08cfe)_

<!-- entry id=GR-0011 source=TASK-035 sha=1d08cfe status=active -->
- **GR-0011** - Concrete numeric invariants asserted in operator docs (e.g. 'N transactions per intake iteration') must be pinned by a doc test that asserts the documented number against the live benchmark/source constant; without that test, prose silently drifts from behavior — TASK-035 found the runbook claiming one transaction where the realigned path actually commits two. _(TASK-035 @1d08cfe)_

<!-- entry id=GR-0012 source=V2-005 sha=d352e45 status=active -->
- **GR-0012** - A typed discriminated-union config field needs negative tests for malformed *object* variants — a present-but-disabled flag (`catch_all: false`) and mixed/partial-key objects — not only the wrong-primitive case (string scope); the union can still admit structurally-malformed objects that satisfy no intended variant unless each invalid shape is explicitly rejected. V2-005 was reopened specifically to add this parametrized object-scope negative coverage. _(V2-005 @d352e45)_

## Architecture Gotchas

<!-- entry id=AG-0001 source=TASK-034 sha=1d08cfe status=active -->
- **AG-0001** - Adding a new package under src/praetor/ (e.g. codification) requires adding it to the scope-guard allowlist in tests/contracts/test_scope_guard.py, or the contracts test suite fails. The allowlist is opt-in, not auto-discovered. _(TASK-034 @1d08cfe)_

<!-- entry id=AG-0002 source=TASK-034 sha=1d08cfe status=active -->
- **AG-0002** - The org-config sweep deliberately observes the full supplied telemetry corpus (no correlation-window/anchor-slice filter) and only empirically proposes principals, assets, and process-chain admin patterns; statute/policy sections, subnet membership, and never-contain are operator-authored placeholders, never inferred. A proposed config that omits these is by-design, not a bug. _(TASK-034 @1d08cfe)_

<!-- entry id=AG-0003 source=task-001 sha=38e3ca0 status=active -->
- **AG-0003** - The project uses `hatchling` + `src/` layout; `praetor` is not importable by pytest unless the editable install has been run first (`pip install -e ".[dev]"` from the repo root). Skipping this step causes a silent `ImportError` even when all source files are present, because pytest does not auto-discover packages under `src/` without the install. _(task-001 @38e3ca0)_

<!-- entry id=AG-0004 source=task-002 sha=6fccc79 status=active -->
- **AG-0004** - When a Pydantic v2 contract model field is typed `Literal["1"]` (e.g., `schema_version`) and the module-level default constant is declared as plain `str`, mypy raises an `[assignment]` error on every model that uses it. Fix: declare the type alias `SchemaVersionV1 = Literal["1"]` and the constant `SCHEMA_VERSION_V1: SchemaVersionV1 = "1"` in `_base.py`, then import both everywhere — this eliminates the error without any runtime or behavioral change. _(task-002 @6fccc79)_

<!-- entry id=AG-0005 source=task-002 sha=6fccc79 status=active -->
- **AG-0005** - All Praetor Pydantic v2 contract models must use `ConfigDict(extra="forbid")`; without it, unknown keys are silently accepted, violating the strict-contract guarantee that downstream consumers (hashing, policy gate, ledger) rely on. _(task-002 @6fccc79)_

<!-- entry id=AG-0006 source=TASK-003 sha=3112332 status=active -->
- **AG-0006** - The `EMPTY_BUNDLE` sentinel preimage is canonically pinned as the string `"praetor:v1:empty_bundle"` in `docs/contracts.md` §7; this value must be reproduced verbatim in `canonical.py`. Any reimplementation that changes this string silently diverges from every other site that hashes against the same sentinel, with no test failure at the point of divergence. _(TASK-003 @3112332)_

<!-- entry id=AG-0007 source=TASK-003 sha=3112332 status=active -->
- **AG-0007** - All `praetor:v1:*` domain string literals must live exclusively in `src/praetor/hashing/domains.py` (docs/contracts.md §2). Inline literals elsewhere break the single-source guarantee; enforcement is a grep check that must return empty for any path outside that module. _(TASK-003 @3112332)_

<!-- entry id=AG-0008 source=TASK-004 sha=106afb0 status=active -->
- **AG-0008** - Principal identity attached to write records must come from `verified_record_identity`, not from caller-supplied fields. If the caller passes an identity string that differs from the token-derived principal, `SelfAssertedIdentityError` is raised. Bypassing this check (e.g. accepting a caller's `submitted_by` field directly) opens an identity-spoofing hole on every record type. _(TASK-004 @106afb0)_

<!-- entry id=AG-0009 source=TASK-004 sha=106afb0 status=active -->
- **AG-0009** - Ledger append, directive emission, and feed export are classified as `InternalOperation` values and are explicitly excluded from the external auth router; `guard_internal_only` raises `InternalOperationError` if any of them is passed to `authenticate_external_write`. Future tasks wiring new write endpoints must route through `authenticate_external_write` (which rejects `InternalOperation` inputs), not call the surface-specific authenticators directly. _(TASK-004 @106afb0)_

<!-- entry id=AG-0010 source=TASK-005 sha=beacec5 status=active -->
- **AG-0010** - A fresh SQLite file defaults to `journal_mode=delete`, so a verify-only startup guard that checks journal mode will reject a clean first boot. The bootstrap step (`init_state_dir`) must apply the WAL PRAGMA once before the guard is invoked; the guard itself must remain verify-only and never apply PRAGMAs, or idempotency is lost on subsequent starts. _(TASK-005 @beacec5)_

<!-- entry id=AG-0011 source=TASK-005 sha=beacec5 status=active -->
- **AG-0011** - SQLite does not support nested `BEGIN IMMEDIATE`; a `critical_transaction` context manager must track an in-flight sentinel per connection and raise on a nested call rather than proceeding silently. Without this guard, a nested call appears to succeed but commits the inner block independently of the outer, destroying atomicity with no error. _(TASK-005 @beacec5)_

<!-- entry id=AG-0012 source=TASK-005 sha=beacec5 status=active -->
- **AG-0012** - Startup guard exceptions must carry a numeric `exit_code` attribute but must not call `sys.exit()` directly; the application entrypoint (a separately owned task) is responsible for mapping `exc.exit_code` to `sys.exit()`. Placing `sys.exit()` inside library/guard code makes the module impossible to unit-test without subprocess spawning and couples library behavior to process lifecycle. _(TASK-005 @beacec5)_

<!-- entry id=AG-0013 source=TASK-005 sha=beacec5 status=active -->
- **AG-0013** - On Windows, `msvcrt.locking` requires the file cursor to be positioned within an already-written byte range; the lock file must have a sentinel byte written to it before the lock call, or `locking` raises an OS error. This diverges from POSIX `flock`, which locks the file descriptor regardless of content. _(TASK-005 @beacec5)_

<!-- entry id=AG-0014 source=TASK-006 sha=d8533db status=active -->
- **AG-0014** - SQLite foreign-key enforcement is OFF by default and must be re-enabled with `PRAGMA foreign_keys=ON` at every connection open, not once at database creation. Omitting it silently accepts FK-violating writes on that connection with no error, corrupting referential integrity invisibly. _(TASK-006 @d8533db)_

<!-- entry id=AG-0015 source=TASK-006 sha=d8533db status=active -->
- **AG-0015** - The SQLite pattern for enforcing 'at most one non-terminal row per key' is a partial unique index (e.g., `CREATE UNIQUE INDEX … ON attempts(alert_identity) WHERE state NOT IN ('completed','aborted')`), not application-level checks. The index enforces the invariant at the storage engine level regardless of how the insert is issued, making it robust to future code paths that accidentally bypass the application guard. _(TASK-006 @d8533db)_

<!-- entry id=AG-0016 source=TASK-006 sha=d8533db status=active -->
- **AG-0016** - A duplicate-intake loser must re-query the completed edict table *after* acquiring `critical_transaction` (BEGIN IMMEDIATE), not before; the pre-lock read is stale and will miss a winner that committed between the loser's first read and its lock acquisition. Without the post-lock re-check, the loser allocates a fresh attempt against an already-final decision. _(TASK-006 @d8533db)_

<!-- entry id=AG-0017 source=TASK-006 sha=d8533db status=active -->
- **AG-0017** - A revocation write must atomically insert both the `DirectiveRevocationRecord` JSON row and the corresponding `revocation_feed_outbox` row inside one `critical_transaction`. A revocation record without an outbox row is an undetectable silent gap for the feed exporter (Task 11), which has no reconciliation path back to the record table. _(TASK-006 @d8533db)_

<!-- entry id=AG-0018 source=TASK-007 sha=d8533db status=active -->
- **AG-0018** - Any outbox that calls an external system must write a `pending` row *before* issuing the call, then update to the definitive outcome afterward. Reversing the order (call-then-write) means a process crash between the call and the write leaves no durable signal for recovery, making in-flight work silently unretriable even though the external side effect may already have executed. _(TASK-007 @d8533db)_

<!-- entry id=AG-0019 source=TASK-007 sha=d8533db status=active -->
- **AG-0019** - Outbox outcome enums must carry a third state — `unknown` — for timeout and ambiguous responses, distinct from both `succeeded` and `failed`. Collapsing `unknown` into `failed` either suppresses safe retries (if `failed` is treated as terminal) or risks double-execution on a non-idempotent backend (if `failed` is treated as retryable); `unknown` is the only state that correctly preserves optionality for the recovery loop. _(TASK-007 @d8533db)_

<!-- entry id=AG-0020 source=TASK-008 sha=d8533db status=active -->
- **AG-0020** - A multi-channel alert outbox must be split into two tables: one for the alert payload record (`*_outbox`) and one for per-channel delivery attempts (`*_delivery_attempts`) with a `channel` string column. Future channels (SIEM, chat, ticket, SOAR) then add rows rather than columns and require no schema migration; partial per-channel delivery failure is naturally trackable and retryable without touching the payload record. _(TASK-008 @d8533db)_

<!-- entry id=AG-0021 source=TASK-008 sha=d8533db status=active -->
- **AG-0021** - Wiring a new subsystem outbox (e.g., `alerts.outbox`, `tickets.outbox`) into `open_state_store` with a module-level import creates a circular import through `state.__init__`; place the import inside the function body (lazy import) to break the cycle. This applies to any new package that is both imported by `state` and imports from `state`. _(TASK-008 @d8533db)_

<!-- entry id=AG-0022 source=TASK-008 sha=d8533db status=active -->
- **AG-0022** - Outbox emit functions that combine persist-then-deliver should accept a `deliver` boolean flag (default `True`) so startup refusal paths and early-boot callers can invoke persist-only without triggering delivery — which may itself fail during boot. Omitting this flag forces callers to duplicate the persistence write or skip durability entirely. _(TASK-008 @d8533db)_

<!-- entry id=AG-0023 source=TASK-009 sha=1810fba status=active -->
- **AG-0023** - Praetor policy-section models (e.g., `directive_lifetime`, `probe_rate`) must declare integer fields as `StrictInt` or guard them with a pre-Pydantic `_require_positive_int` validator; Pydantic's default `int` silently coerces YAML-quoted strings like `"300"` to valid integers, accepting configs the spec requires to be rejected without surfacing any validation error. _(TASK-009 @1810fba)_

<!-- entry id=AG-0024 source=TASK-009 sha=1810fba status=active -->
- **AG-0024** - When loading a stored org-config snapshot from the database, always recompute the binding hash and assert it matches the stored `snapshot_hash` field; accepting the persisted hash value at face value silently passes tampered or corrupted records through to policy evaluation with no error. The re-verification must happen at fetch time, not only at write time. _(TASK-009 @1810fba)_

<!-- entry id=AG-0025 source=TASK-009 sha=1810fba status=active -->
- **AG-0025** - Internal hashing and serialization exceptions (e.g., `CanonicalSerializationError`) must be caught inside the snapshot-hash computation helper and re-raised as a structured preflight domain error (e.g., `PreflightError.invalid_binding_value`) before propagating to callers; leaking implementation-level exceptions breaks the preflight abstraction and gives callers no actionable recovery path. _(TASK-009 @1810fba)_

<!-- entry id=AG-0026 source=TASK-010 sha=198f6ff status=active -->
- **AG-0026** - The ledger link-hash genesis preimage uses the literal string `"null"` for the previous-hash slot (not Python `None`, an empty string, or a JSON null token), as pinned in `docs/contracts.md` §7a. Any reimplementation that deviates from this sentinel silently produces a divergent hash with no failure at the point of divergence, mirroring the `EMPTY_BUNDLE` hazard documented in AG-0006. _(TASK-010 @198f6ff)_

<!-- entry id=AG-0027 source=TASK-010 sha=198f6ff status=active -->
- **AG-0027** - A hash chain can detect middle deletions and tampering but cannot detect tail truncation (removal of the most recent records) without an externally stored tip anchor; `verify_chain()` on a silently-shortened chain returns success. Production deployments must record an out-of-band tip anchor to close this gap, and the limitation must be explicitly documented in any ledger integrity surface. _(TASK-010 @198f6ff)_

<!-- entry id=AG-0028 source=TASK-010 sha=198f6ff status=active -->
- **AG-0028** - `append_ledger_record` enforces that it is called inside an active `critical_transaction` and raises an error otherwise. Future tasks wiring edict, revocation, or emergency-containment write paths to the ledger must wrap the domain write and the ledger append together in a single `critical_transaction` to preserve both atomicity and chain continuity. _(TASK-010 @198f6ff)_

<!-- entry id=AG-0029 source=TASK-010 sha=198f6ff status=active -->
- **AG-0029** - A Pydantic model with an embedded self-validating hash field (one that recomputes and asserts `snapshot_hash` matches `snapshot_content` at instantiation) will reject any test fixture that uses a placeholder or hardcoded hash string. Fixtures for such models must compute the correct hash dynamically at construction time, typically via a shared conftest helper. _(TASK-010 @198f6ff)_

<!-- entry id=AG-0030 source=TASK-011 sha=67a751e status=active -->
- **AG-0030** - When a feed exporter maintains a metadata counter (e.g., `last_verified_exported_sequence`), it must be reconciled against the actual on-disk file contents before being trusted; if the file is missing, empty, or contains fewer validated lines than the counter claims, the feed must immediately be marked unhealthy. Trusting persisted metadata that outpaces the physical artifact silently hides export failures with no observable error signal. _(TASK-011 @67a751e)_

<!-- entry id=AG-0031 source=TASK-011 sha=67a751e status=active -->
- **AG-0031** - When reading back a JSONL feed file for prefix validation, schema-invalid lines (Pydantic `ValidationError`, shape mismatches) must be caught and re-raised as a structured domain error (e.g., `FeedChecksumError`) that marks the feed unhealthy — not propagated as a raw exception crash. Letting validation errors bubble uncaught leaves the exporter in an indeterminate state with no recovery path. _(TASK-011 @67a751e)_

<!-- entry id=AG-0032 source=TASK-011 sha=67a751e status=active -->
- **AG-0032** - A file-based sequential exporter that marks rows exported in the database *after* writing them to disk must re-verify that the target sequence number is not already present in the file before appending on crash recovery, preventing duplicate lines. Unlike the DB-level pending-before-call pattern (AG-0018), file-append idempotency requires a physical file scan at recovery time, not a status-column check. _(TASK-011 @67a751e)_

<!-- entry id=AG-0033 source=TASK-012 sha=1a8f6a8 status=active -->
- **AG-0033** - When building a `DecisionEdict`, the evidence bundle hash must be resolved exactly once into a single local variable and passed to both the `decision_id` derivation and the stored `evidence_bundle_hash` field; recomputing or re-reading the hash independently at each call site within the same builder creates a silent divergence between the two values — especially when the hash is an EMPTY_BUNDLE substitute — with no failure at the point of divergence. _(TASK-012 @1a8f6a8)_

<!-- entry id=AG-0034 source=TASK-012 sha=1a8f6a8 status=active -->

<!-- entry id=AG-0035 source=TASK-012 sha=1a8f6a8 status=active -->
- **AG-0035** - A recovery builder that appends a ledger edict must guard with a `ledger_has_edict_for_decision_id` check before appending; omitting this guard duplicates the edict in the crash window where the ledger append committed but the subsequent attempt state-transition did not, causing two `DecisionEdict` rows for the same `decision_id` on the next startup scan. _(TASK-012 @1a8f6a8)_

<!-- entry id=AG-0036 source=TASK-013 sha=0873e3e status=active -->
- **AG-0036** - When a fake/stub provider is shared across multiple test scenarios in a harness, per-scenario behavioral configuration must be keyed by `scenario_id` (e.g., `scenario_modes: dict[str, FakeProviderMode]`), not set at the instance level. Instance-scoped mode causes scenario-to-scenario bleed when scenarios sharing one provider instance require different behaviors. _(TASK-013 @0873e3e)_

Treating a content-quality defect (fabricated citation) as a provider infrastructure failure would bypass citation-validity checks and incorrectly classify a systematic content problem as a transient outage. _(TASK-013 @0873e3e)_

A flat filter silently leaks `raw_source` values embedded in normalized fields; the TASK-014 code review caught this gap after initial implementation and added dedicated regression coverage. _(TASK-014 @fa72dec)_

<!-- entry id=AG-0039 source=TASK-014 sha=fa72dec status=active -->

<!-- entry id=AG-0040 source=TASK-015 sha=aca6c61 status=active -->

Any extension of field-path resolution logic must reproduce this exclusion or citations will silently re-expose raw source provenance through the judgment layer. _(TASK-015 @aca6c61)_

<!-- entry id=AG-0041 source=TASK-015 sha=aca6c61 status=active -->

<!-- entry id=AG-0042 source=TASK-016 sha=113014f status=active -->
- **AG-0042** - A policy eligibility evaluator must enumerate every outcome branch explicitly with a return statement; an implicit fall-through silently produces a no-containment result without setting a fault flag, making the logic gap indistinguishable from a legitimate deny. TASK-016 required a dedicated hardening pass to close this after initial implementation — the 'SID-backed but insufficiently corroborated' branch was the specific gap caught. _(TASK-016 @113014f)_

<!-- entry id=AG-0043 source=TASK-017 sha=113014f status=active -->

Placing any of those writes inside the gate transaction couples the gate to ledger append before engine wiring exists and breaks the serializable emit guarantee. _(TASK-017 @113014f)_

<!-- entry id=AG-0044 source=TASK-017 sha=113014f status=active -->
- **AG-0044** - `NeverContainSnapshotRecord` must be written atomically with `DecisionEdict` at engine edict-append time, not inside the PolicyGate transaction; the gate should return `live_never_contain_entries` for the engine to consume so that the full live list is captured at the moment of the edict commit. Writing the snapshot inside the gate alone creates a window between two separate commits where the directive exists without its audit snapshot. _(TASK-017 @113014f)_

<!-- entry id=AG-0045 source=TASK-017 sha=113014f status=active -->
- **AG-0045** - `reconcile_policy_state` (startup step 6) must skip — not re-register — outstanding directive rows that have no matching ledger edict (the half-committed case where the directive row committed but the ledger append did not); re-registering idempotency for these orphans would permit a second independent emission on the next intake instead of letting the engine crash-recovery path (steps 4/5) resolve them. This is verified by `test_reconcile_skips_idempotency_when_ledger_edict_missing`. _(TASK-017 @113014f)_

<!-- entry id=AG-0046 source=TASK-018 sha=536aa57 status=active -->
- **AG-0046** - Raising a rollback sentinel (e.g., `_PolicyGateRollback`) inside a `critical_transaction` block triggers ROLLBACK on *all* writes in that block — including failure-counter increments, breaker-state updates, and queued outbox alerts. Side effects that must survive a race-loser abort must be committed in a separate, independently-committed transaction *after* the `with critical_transaction(...)` block exits; catch a distinct exception type outside the block and invoke a separate committed helper (e.g., `_record_rate_limit_failure`) to persist the failure record. _(TASK-018 @536aa57)_

<!-- entry id=AG-0047 source=TASK-018 sha=536aa57 status=active -->
- **AG-0047** - A circuit breaker `is_open` check implemented as a plain `SELECT is_open FROM ...` never auto-recovers via window-elapse; the check itself must also advance the window start timestamp — resetting `is_open=0` when `now >= window_start + window_seconds` — so that elapsed time can close the breaker. A read-only open-check creates a permanently-open breaker state with no exit. _(TASK-018 @536aa57)_

<!-- entry id=AG-0048 source=TASK-018 sha=536aa57 status=active -->
- **AG-0048** - A circuit breaker that blocks the exact operation that generates its success signals (e.g., a containment breaker that blocks `auto_contain`) can never accumulate successes to close itself; window-elapse is the only viable auto-recovery mechanism for such a breaker.
