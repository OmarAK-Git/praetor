  AG-0004 (active) [contracts]: When a Pydantic v2 contract model field is typed `Literal["1"]` (e.g., `schema_version`) and the module-level default constant is declared as plain `str`, mypy raises an `[assignment]` error on every model that uses it. Fix: declare the type alias `SchemaVersionV1 = Literal["1"]` and the constant `SCHEMA_VERSION_V1: SchemaVersionV1 = "1"` in `_base.py`, then import both everywhere — this eliminates the error without any runtime or behavioral change.
  AG-0005 (active) [contracts]: All Praetor Pydantic v2 contract models must use `ConfigDict(extra="forbid")`; without it, unknown keys are silently accepted, violating the strict-contract guarantee that downstream consumers (hashing, policy gate, ledger) rely on.
  AG-0006 (active) [hashing]: The `EMPTY_BUNDLE` sentinel preimage is canonically pinned as the string `"praetor:v1:empty_bundle"` in `docs/contracts.md` §7; this value must be reproduced verbatim in `canonical.py`. Any reimplementation that changes this string silently diverges from every other site that hashes against the same sentinel, with no test failure at the point of divergence.
  AG-0007 (active) [hashing]: All `praetor:v1:*` domain string literals must live exclusively in `src/praetor/hashing/domains.py` (docs/contracts.md §2). Inline literals elsewhere break the single-source guarantee; enforcement is a grep check that must return empty for any path outside that module.
  AG-0008 (active) [auth]: Principal identity attached to write records must come from `verified_record_identity`, not from caller-supplied fields. If the caller passes an identity string that differs from the token-derived principal, `SelfAssertedIdentityError` is raised. Bypassing this check (e.g. accepting a caller's `submitted_by` field directly) opens an identity-spoofing hole on every record type.
  AG-0009 (active) [auth]: Ledger append, directive emission, and feed export are classified as `InternalOperation` values and are explicitly excluded from the external auth router; `guard_internal_only` raises `InternalOperationError` if any of them is passed to `authenticate_external_write`. Future tasks wiring new write endpoints must route through `authenticate_external_write` (which rejects `InternalOperation` inputs), not call the surface-specific authenticators directly.
  AG-0010 (active) [sqlite]: A fresh SQLite file defaults to `journal_mode=delete`, so a verify-only startup guard that checks journal mode will reject a clean first boot. The bootstrap step (`init_state_dir`) must apply the WAL PRAGMA once before the guard is invoked; the guard itself must remain verify-only and never apply PRAGMAs, or idempotency is lost on subsequent starts.
  AG-0011 (active) [sqlite]: SQLite does not support nested `BEGIN IMMEDIATE`; a `critical_transaction` context manager must track an in-flight sentinel per connection and raise on a nested call rather than proceeding silently. Without this guard, a nested call appears to succeed but commits the inner block independently of the outer, destroying atomicity with no error.
  AG-0012 (active) [startup]: Startup guard exceptions must carry a numeric `exit_code` attribute but must not call `sys.exit()` directly; the application entrypoint (a separately owned task) is responsible for mapping `exc.exit_code` to `sys.exit()`. Placing `sys.exit()` inside library/guard code makes the module impossible to unit-test without subprocess spawning and couples library behavior to process lifecycle.
  AG-0013 (active) [sqlite]: On Windows, `msvcrt.locking` requires the file cursor to be positioned within an already-written byte range; the lock file must have a sentinel byte written to it before the lock call, or `locking` raises an OS error. This diverges from POSIX `flock`, which locks the file descriptor regardless of content.
  AG-0014 (active) [sqlite]: SQLite foreign-key enforcement is OFF by default and must be re-enabled with `PRAGMA foreign_keys=ON` at every connection open, not once at database creation.
